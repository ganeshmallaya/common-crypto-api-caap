PQC-Agile Cryptography · Reference Architecture DRAFT · REV 01 FOR WG REVIEW

Common Crypto API // working name — CAAP / PACE TBD

A vendor-neutral abstraction that lets anything touching cryptography — applications, workloads, endpoints, hardware roots of trust — invoke operations by intent while algorithm choice is resolved by policy. Plug-and-play rests on two stable contracts and a compatibility path for the crypto that already exists.

The Plug-and-Play Thesis

two contracts, one broker
↑ North Contract
Consumer API
Stable, algorithm-agnostic operations. Any consumer that speaks this — or the PKCS#11 shim — plugs in without knowing what runs underneath.

↑ PROVIDERS
↓ South Contract
Provider SPI
The contract backends implement. Any library, HSM, KMS, TPM or enclave that satisfies the SPI registers as a provider — no core changes.
describe_capabilities · keygen
sign · verify · encaps · decaps
derive · wrap · attest
WHY IT WORKS
Consumers depend only on the north contract; backends satisfy only the south contract. Neither knows the other exists. New algorithms, new hardware, and policy changes all flow through the broker without touching consumer code — that is the entire agility payoff, expressed as an architecture rather than a promise.

Signed Profile Distribution
provenance · downgrade defense
Provenance matters here more than anywhere: the policy profile is a catastrophic single point of downgrade if unsigned. Profiles are signed at source, verified before use, and resolution rejects any result weaker than the caller's stated minimum — even when a weaker algorithm is technically available.
02

Deployment Topologies

same contracts, different placement
TOPOLOGY A
In-Process Library
Broker linked directly into the app. Lowest latency, no network hop.
Fits: HSM-adjacent, latency-critical, single-tenant services.
TOPOLOGY B
Local Daemon / Sidecar
Broker as a per-host or per-pod agent. Apps call over a local socket.
Fits: Kubernetes, service mesh, mixed-language estates.
TOPOLOGY C
Central Crypto Service
Broker as a networked, HA service. Centralized policy enforcement and audit.
Fits: enterprise-wide governance, shared HSM pools, CLM platforms.
TOPOLOGY D
Hybrid / Tiered
Local broker for hot ops, central service for policy and inventory sync.
Fits: the realistic production default at scale.
HARD BOUNDARY
Constrained devices, boot-time roots, and line-rate datapaths sit outside this diagram. A 32KB microcontroller, a measured-boot root of trust, or a MACsec datapath cannot host a broker or call a policy service — the algorithm is fixed at build time. This is a datacenter and enterprise-workload architecture, not a universal one. Saying that plainly is a feature at the WG table, not a weakness.

Agility + Hybrid
  • DeriveSecret · Wrap / Unwrap

  • Policy-driven resolution live
LEVEL 2 · OPTIONAL

  • Non-extractable key guarantees
  • FIPS-validated backend attestation
  • Provider attestation format
  • Signed policy provenance enforced
04

What to Build First

the concrete on-ramp
1
Define both contracts as a machine-readable IDL
North (Consumer API) + South (Provider SPI) in one versioned schema — protobuf, OpenAPI, or CDDL. This artifact, not the prose, is what stops vendors diverging.
FOUNDATION
2
Reference broker + one consumer binding
Prove the spec is buildable as written. Ambiguities surface here before the field. Open source from day one.
PROVES SPEC
3
Two providers: liboqs (software) + PKCS#11 (HSM)
One software, one hardware — enough to demonstrate hot-swap and that the south contract holds across radically different backends.
PROVES SPI
4
PKCS#11 compatibility shim
The fastest path to "works with everything that touches crypto today." Existing PKCS#11 apps plug in with zero code change — your strongest live demo for skeptics.
ADOPTION UNLOCK
5
Composite path + one hybrid identifier end-to-end
ECDSA + ML-DSA through the orchestrator, resolved by a signed policy profile. Swap the profile, get a different cert, zero code change — the whole thesis in one demo.
PROVES AGILITY
6
Test vectors + conformance suite
Runnable self-certification per level. This is what turns a design doc into something a working group can adopt and vendors can claim against.
STANDARDS-READY
SEQUENCING
Steps 1, 4 are the ones nobody else has done and the ones that carry the argument. Build the IDL first and the PKCS#11 shim early — together they answer the two questions every expert will ask: "how do you stop vendor drift" and "how does this work with what I already run."
