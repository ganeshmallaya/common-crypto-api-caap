# Cryptographic API Agility: The CCP Standard vs. the IBM arXiv Papers — A Prior-Art Analysis for Original Research

## TL;DR
- The **CCP (Cryptographic Control Plane) Standard** and the two **IBM Research Zurich arXiv papers** (2606.13425, 2606.13445) are **independent, parallel efforts** that converged on the same core idea — decoupling cryptographic *intent* from *execution* — but at different layers: CCP is a vendor-neutral **enterprise architecture standard** (published by startup ANKATech Solutions INC, backing its ANKASecure product), while the IBM papers are a **rigorous academic API-design contribution** (a seven-dimension assessment framework plus a gRPC/Protocol Buffers intent-based API). Neither cites the other; there is no personnel overlap.
- The IBM papers go far deeper on **API mechanics** (scopes, templates, the binding chain, key evolution operations, 13 design principles) and provide a **falsifiable evaluation** of six real systems; CCP goes further on **organizational framing** (six-level maturity model, migration program phases, governance narrative) but is documentation-only with **no proto/OpenAPI/SDK** in its repo and explicitly defers the API contract as an open question.
- The clearest **openings for original research** are the areas *both* leave unaddressed: business/purpose-level intent (C2.3/C2.4) and context inference (C4.4), policy-driven *automatic* migration (E1.4/E2.3+), formal safety proofs of scope substitutability, empirical developer/performance studies, protocol-layer integration, and a bridge between the API layer (IBM) and the enterprise control-plane/orchestration layer (CCP) — none of which either work delivers.

## Key Findings

**1. Provenance and relationship.** The IBM papers are by Navaneeth Rameshan (vme@zurich.ibm.com) and Grégoire Messmer (Gregoire.Messmer@ibm.com), IBM Research Europe, Zurich, both submitted 11 June 2026 (v1), CC BY 4.0, and presented at the MAgiCS workshop co-located with Eurocrypt 2026 (ideas first aired at the PKI Consortium conference in Kuala Lumpur, November 2025). The CCP Standard (v0.9 "Working Draft," published May 2026, CC BY 4.0) was initiated by **ANKATech Solutions INC**, a Delaware-incorporated deeptech company founded in 2025, whose commercial product **ANKASecure©** is the self-declared reference implementation. A dedicated subagent search confirmed: neither the CCP website, its GitHub repo, nor ANKATech material cites the IBM papers or uses IBM's distinctive vocabulary ("scope," "intent vocabulary," "template," "binding chain"); conversely, the IBM papers never mention CCP or ANKATech (their evaluation set is PKCS#11, OpenSSL 3.0, JCA, Google Tink, AWS KMS, HashiCorp Vault Transit). No shared personnel were found. They are independent efforts that both surfaced in mid-2026 riding the 2024 NIST FIPS 203/204/205 wave.

**2. They operate at different layers and are complementary, not duplicative.** IBM explicitly scopes its contribution to the **cryptographic provider API layer**, and in its own Related Work says a "complete agility stack requires both: provider APIs that support intent-based creation and key evolution (our contribution), combined with orchestration layers for policy distribution and migration coordination." CCP is exactly such an **orchestration/control-plane layer** — but defined as prose architecture, not as an API. This is the single most important framing for an original paper: the two works are two halves of the same stack, and neither fully builds the bridge.

**3. CCP is conceptually parallel but far less rigorous and specified.** CCP's site is a polished single-page document; its GitHub repo (`ccp-standard/standard`, 2 stars, 7 commits) is **documentation-only** — one 79.5 KB `index.html`, plus README, CHANGELOG, GOVERNANCE, CONTRIBUTING and a `docs/` folder — with **no `.proto`, no OpenAPI, no SDK, no reference code**. CCP itself lists "Standardized CCP API specification" as open question #1, conceding it "does not specify a wire protocol or API contract." By contrast, the IBM API paper specifies seven gRPC services (~90 RPCs), concrete Protocol Buffers message types, an intent enum vocabulary, and a worked ECDSA→ML-DSA migration.

**4. The three gaps IBM identifies in deployed systems are real and well-evidenced.** Across six systems, IBM finds none reaches C2.2 (intent-based key creation), none reaches C5.3+ (cryptographic governance as distinct from access control), and none reaches E1.3 (explicit algorithm transformation). These are individually sufficient to keep the PQC transition a per-call-site software-engineering problem.

## Details

### A. The CCP (Cryptographic Control Plane) Standard

**Mission / problem statement.** CCP's thesis is that "Cryptography is the last critical infrastructure layer still living inside application code." It argues cryptography should be "infrastructure, not implementation," and draws an explicit historical analogy: networking → Software-Defined Networking; identity/credentials → IAM/PAM; secrets → Vault/secrets management; and now cryptography → Cryptographic Control Plane. The core move is that applications reference a **Key ID** and a requested operation (encrypt/sign/verify) only — "no algorithm name, no library import, no cipher selection occurs at the application level" — while the Control Plane resolves intent against active policy and executes.

**CAPA framework — five pillars.** Crypto Agility Posture Architecture (note: the website expands CAPA as "Crypto Agility Posture Architecture," while the GitHub README expands it as "Crypto-Agility Posture Assessment" — an internal inconsistency): (1) Crypto-Agility, (2) Cryptographic Sovereignty, (3) Frictionless Modernization, (4) Policy-Driven Governance, (5) Regulatory Compliance.

**Maturity model — inconsistent between website and repo.** The website presents **six levels L1–L6**: L1 Embedded cryptography, L2 Managed cryptography, L3 Cryptographic Control Plane, L4 Cryptographic agility, L5 Optimized cryptography, L6 Continuous crypto evolution. The GitHub README presents a **different six-level scale (0–5)**: Ad Hoc, Aware, Managed, Orchestrated, Adaptive, Autonomous. This discrepancy is a genuine weakness worth citing.

**Minimum capabilities (conformance).** Five mandatory capabilities: (1) cryptographic abstraction layer, (2) policy-driven algorithm governance, (3) algorithm lifecycle management (incl. PQC migration without code change), (4) key lifecycle orchestration (HSM/KMS integration required), (5) cryptographic audit and traceability.

**Reference architecture.** Four layers: Applications & services (reference by Key ID only); the Cryptographic Control Plane (crypto-abstraction layer, crypto-agility engine, streaming operations, key lifecycle orchestration, policy governance engine); Key infrastructure (HSM/KMS/CA/PKI — orchestrated, not replaced); and an Algorithm catalog (classical + PQC ML-KEM/ML-DSA/SLH-DSA + composite hybrids, activated/deactivated by policy).

**Migration program.** Three parallel tracks (Greenfield, Brownfield-critical, Brownfield-general) across four phases: Phase 01 Discovery & Risk (2–6 weeks), Phase 02 Governance (4–8 weeks), Phase 03 Control Plane Deployment (4–12 weeks), Phase 04 Incremental PQC Migration (12–36 months).

**PQC stance.** HNDL ("Harvest Now, Decrypt Later") is the stated proximate cause; hardcoded cryptography the underlying condition. Aligned to NIST, ETSI, BSI, ISO/IEC. Open questions explicitly ask how CCP should relate to NIST SP 800-57, SP 800-131A, and ETSI TS 119 312.

**Governance / license / status.** Published by "the CCP Initiative," CC BY 4.0, v0.9 working draft; ANKATech is "founding contributor" and maintains ANKASecure as reference implementation. ANKASecure claims 125+ algorithms across 21+ families, 40+ composite hybrids, 14+ standards. No standards-body affiliation (IETF/NIST/ETSI/OASIS) is claimed; the relationship to those bodies is posed as an open question. ANKATech is a member of the PKI Consortium (PKIC).

**Visual/diagrammatic style (per subagent inspection of `index.html` CSS).** A dark-mode, single-page, "technical spec / dev-tool" aesthetic — **NOT hand-drawn or whiteboard-sketch**. Palette: near-black background (`--bg: #0a0a0b`), off-white text (`#f0f0ee`), a signature bright lime/chartreuse accent (`--accent: #c8f55a`), and red (`#ff5f5f`) for "Before"/threat states. Typography: **Instrument Serif** (italic serif display headings), **DM Mono** (monospace eyebrows/labels/badges/buttons — the "spec/terminal" feel), **DM Sans** (light body). Diagrams are **clean CSS boxes/grids** with border-radius 8px, 1px borders, and literal typographic arrows ("↓", "→", "←"); a faint blueprint grid background in the hero. Before/after blocks are two-column CSS grids: "Before/Without CCP" cells in muted gray with red uppercase mono labels and strikethrough values; "After/With CCP" cells in lime-tinted boxes with lime labels. Single-page smooth-scroll with anchors (#problem, #evolution, #capa, #maturity, #architecture, #migration, #about), fixed translucent blurred top nav, content capped at ~900–1100px width, one responsive breakpoint at 680px.

**CCP's own before/after example (to deliberately avoid duplicating).** CCP's headline concrete example is **algorithm migration of RSA / "AES-256, RSA hardcoded"**: "Without CCP — Change RSA → modify application code → recompile → redeploy… Months. With CCP — Update the cryptographic policy… Hours." It does not show a specific language code snippet; its before/after is architectural boxes ("Application ↓ AES-256, RSA hardcoded → Crypto Library") rather than a source-level diff. Its narrative operations are generic encrypt/sign/verify by Key ID.

### B. IBM Paper 1 — "An Assessment Framework for Application-Level Cryptographic Agility" (2606.13425)

**Seven orthogonal dimensions, two tiers, scored 0–4.** Tier 1 (Decoupling): C1 operation coupling, C2 creation coupling, C3 provider coupling, C4 decoupling mechanism (applied orthogonally to C1–C3), C5 authority. Tier 2 (Enablers): E1 algorithm migration, E2 provider migration. The framework is deliberately non-linear (captures non-hierarchical profiles a linear maturity model cannot).

**Level ladders (key rungs):**
- **C1 (operation):** C1.0 algorithm-specific functions → C1.1 uniform signature w/ parameter leakage → C1.2 key-driven dispatch → C1.3 scope-consistent operations → C1.4 fully managed.
- **C2 (creation) — the crux:** C2.0 raw algorithm parameters → C2.1 named template identifiers → **C2.2 intent-based creation** (e.g., `scope=AUTHENTICATED_ENCRYPTION`) → C2.3 purpose-driven requests (business intent, e.g., `purpose="sign audit logs"`) → C2.4 full contextual inference.
- **C3 (provider):** C3.0 compile-time → C3.1 named → C3.2 uniform API → C3.3 key-driven → C3.4 full agnosticism.
- **C4 (mechanism):** C4.0 hardcoded → C4.1 config file → C4.2 schema-validated → C4.3 policy engine → C4.4 contextual inference.
- **C5 (authority):** C5.0 developer-only → C5.1 single admin → C5.2 role-based access → C5.3 scoped governance domains → C5.4 federated governance. Crucially C5.2 (access control) ≠ C5.3+ (cryptographic selection authority).
- **E1 (algorithm migration):** E1.0 none → E1.1 same-algorithm rotation → E1.2 multi-algorithm versioning → E1.3 explicit algorithm transformation (`TransformKey()`) → E1.4 policy-driven automatic migration.
- **E2 (provider migration):** E2.0 provider-bound → E2.1 manual export/import → E2.2 explicit migration API → E2.3 policy-driven → E2.4 automatic routing.

**Six-system evaluation (Table 1 profiles):**
- **PKCS#11:** C1.1, C2.0, C3.2, C5.0, E1.0, E2.1 (manual C_WrapKey/C_UnwrapKey).
- **OpenSSL 3.0:** C1.1, C2.0, C3.1 (provider name in openssl.cnf, C4.1 on C3), C5.0, E1.0, E2.0.
- **JCA:** C1.1, C2.0, C3.1, C5.0, E1.0, E2.0.
- **Google Tink:** C1.4 (fully managed — highest operation decoupling), C2.1 (KeyTemplate names), C3.0 (compile-time), C5.0, E1.2 (multi-algorithm versioning — best migration mechanism among the six), E2.0.
- **AWS KMS:** C1.1 (SigningAlgorithm leaks), C2.1 (KeySpec), C3.2, C5.2 (IAM access control), E1.1 (same-algorithm rotation), E2.1.
- **HashiCorp Vault Transit:** C1.2 (key-driven dispatch), C2.1, C3.3 (managed keys/HSM routing, enterprise), C5.2, E1.1, E2.1.

**Three pervasive gaps:** (1) partial operation decoupling but *absent* creation decoupling (no system reaches C2.2); (2) access authority exists but cryptographic governance does not (none reaches C5.3+); (3) enablers missing (none reaches E1.3; only Tink reaches E1.2). Each is independently sufficient to block agile migration.

**First-generation "before" code (IBM's own illustrative example).** IBM uses a **Go `rsa.SignPSS`** snippet for signing audit-log entries with RSA-PSS, noting six decisions baked into one call (algorithm, hash SHA-256, key handling, salt length, randomness source, encoding) and that migration cost scales as O(n·m) in call sites × parameter differences. (This is the IBM paper's chosen example — an original paper should avoid re-using RSA-PSS audit-log signing in Go.)

**Nine derived design requirements (R1–R9)** bridge to the companion paper: R1 algorithm-independent operations, R2 intent-based creation vocabulary, R3 stable key identifiers, R4 provider-algorithm separation, R5 temporal decoupling, R6 pluggable policy engine, R7 separation of concerns, R8 three-stage key evolution, R9 discoverable extensibility.

**Post-quantum artifact-size motivation (concrete numbers, verified against FIPS 203/204/205 parameter tables):** ML-DSA-65 public keys are 1,952 bytes vs Ed25519's 32 bytes; ML-KEM-768 has a 1,184-byte public key and 1,088-byte ciphertext vs 32 bytes for an X25519 key share; SLH-DSA-SHA2-128s signatures are 7,856 bytes vs Ed25519's 64 bytes. The paper cites the SHA-1→SHA-256 transition as taking "approximately ten years" despite identical operational interfaces, and cites Lazar et al. (2014): of 269 cryptography-related CVEs, only 17% were flawed algorithm implementations while the remaining **83% stemmed from misuse of cryptographic APIs** by application developers.

### C. IBM Paper 2 — "Intent-Based Cryptographic API Design for Cryptographic Agility" (2606.13445)

**Five foundational properties:** Abstraction, Stability, Temporal Flexibility, Separation, Extensibility.

**Thirteen design principles (10 core, 3 supportive):** P1 Operation Independence, P2 Temporal Decoupling, P3 Intent-Based Specification, P4 Operational Parameter Consistency, P5 Key Abstraction, P6 Key Evolution, P7 Separation of Roles, P8 Algorithm–Implementation Separation, P9 Implementation Portability, P10 Policy Independence; supportive P11 Language Independence, P12 Property Taxonomy, P13 Discoverable Extensibility.

**Architectural vocabulary and the binding chain.** Four abstractions compose into a resolution chain **scope → policy → template → provider**: a *scope* is a named intent category grouping algorithms with a stable invocation contract (same operational parameters); a *template* is an immutable named algorithm configuration with lifecycle states (EXPERIMENTAL → ACTIVE → ACCEPTABLE → DEPRECATED → FORBIDDEN, using CycloneDX CBOM naming); a *policy* resolves scopes to templates and constrains providers/lifecycle (format-agnostic, referenced by name — OPA/Rego, Sentinel, YAML permitted); a *provider* is the execution backend (software lib, HSM, cloud KMS).

**Key API mechanics.** Scopes are per-primitive enums (e.g., `SignatureScope{STANDARD, WITH_CONTEXT, PREHASHED}`, `AeadScope{WITH_AAD, STREAMING, WITH_EXTERNAL_IV}`) composed via a `ScopeSpecification` oneof. Scope boundaries are drawn where **operational parameters** diverge (three-category parameter classification: algorithm parameters → templates; system-generated values → providers; operational parameters → applications). Operations use uniform key-driven dispatch (`SignRequest{key_name, input, oneof scope_params}`). Seven gRPC services (~90 RPCs): CryptoService, StreamingCryptoService, KeyManagementService (CreateKey, RotateKey, TransformKey, MigrateKey, ValidateKeyOperation), KeyEstablishmentService, CryptoPolicyService (incl. EvaluatePolicy, BatchEvaluatePolicy), AlgorithmDiscoveryService, ProviderService. Three key-evolution operations: **RotateKey** (same algorithm), **TransformKey** (new algorithm, same identity — the agility primitive), **MigrateKey** (new provider, five MigrationStrategy options). Five deployment modes from standalone library to fully centralized service, with application code invariant across all five.

**Evaluation of its own API:** reaches C1.3, C2.2, C3.3, C4.3, C5.3–5.4, E1.3, E2.2 — closing exactly the three gaps, while deliberately stopping short of the maximal rungs (C1.4/C2.3/C3.4/E1.4) to preserve flexibility, leaving higher autonomy to an orchestration layer above the API.

**End-to-end scenario (Section 6):** ECDSA→ML-DSA migration of an audit-log signing key in five steps (initial deploy Ed25519ctx → policy update to ML-DSA-65 → TransformKey → template deprecation → provider migration to HSM), with application call `Sign("audit-log-signing-key", data, context)` unchanged throughout.

**A six-fold ("6×") agility improvement** is claimed for shifting from algorithm-specific to intent-based key creation (reported via IBM/press coverage; the paper frames this as the qualitative C2.0/2.1 → C2.2 shift). The scalability of `BatchEvaluatePolicy` on very large key sets is explicitly not quantified — a stated limitation.

### E. Gaps neither addresses (the research openings)
1. **Business/purpose-level intent (C2.3) and contextual inference (C2.4/C4.4)** — IBM explicitly stops at C2.2; CCP has no vocabulary at all. A purpose-driven or context-inferred layer is open.
2. **Policy-driven *automatic* migration (E1.4, E2.3–E2.4)** — IBM leaves automated triggering to an unspecified orchestration layer; CCP asserts it but does not specify it. Nobody has built and evaluated the closed loop.
3. **Formal safety of scope substitutability** — IBM asserts scope boundaries guarantee safe substitution but offers no formal proof or model-checking; an opening for a verified-agility contribution.
4. **Empirical developer-experience and performance studies** — no user study of intent-based APIs, and no latency/throughput benchmarks across the five deployment modes; `BatchEvaluatePolicy` scalability explicitly unmeasured.
5. **Protocol-layer integration** — both are application/data-at-rest oriented; neither reconciles the API layer with TLS/IKEv2 cipher-suite negotiation or with PKI/certificate agility (RFC 7696 territory).
6. **The bridge itself** — a concrete, evaluated architecture that connects the IBM provider API (bottom) to a CCP-style governed control plane (top) does not exist in either work.
7. **CBOM feedback loop** — IBM notes C2.2 systems have the metadata for automated CBOM generation but does not build the discovery→policy→transformation loop.

### F. Wider landscape (for situating the contribution)
- **RFC 7696** (Housley, BCP 201, Nov 2015): the foundational IETF guidance on cryptographic algorithm agility and mandatory-to-implement selection — but protocol/negotiation-level, not application-API-level.
- **IETF PQUIP** WG (Kampanakis, Ounsworth): post-quantum use in protocols.
- **NIST:** FIPS 203/204/205 (Aug 2024); SP 800-131A Rev. 3 (draft, Oct 2024); **NIST IR 8547** initial public draft (Nov 2024), which states verbatim: 112-bit-security public-key algorithms (RSA, ECDSA, ECDH, DSA, FFDH) "deprecated after 2030, disallowed after 2035," and 128-bit-and-higher "disallowed after 2035," with a goal of "widespread PQC adoption by 2035"; SP 1800-38 / NCCoE Migration to PQC project; "Considerations for Achieving Crypto Agility" (2025).
- **NSA CNSA 2.0** (Sept 2022): ML-KEM-1024, ML-DSA-87, AES-256, SHA-384/512; software/firmware signing exclusive by 2030, networking by 2030, OS/web/cloud by 2033; new NSS acquisitions CNSA 2.0 by 1 Jan 2027; NSM-10 target 2035.
- **EU/other:** NIS2 Article 21, ENISA guidance referencing NIST; NCSC-UK Phase 3 complete by 2035; Executive Order 14144 requiring TLS 1.3 (or successor) across federal systems by 2 Jan 2030.
- **OASIS:** KMIP 2.1 and PKCS#11 3.0 (both 2020) — key-management interoperability and token interface; PKCS#11 3.x adds some mechanism-agility but remains C2.0 per IBM.
- **Provider architectures:** OpenSSL 3.x provider model, Java JCA/JCE provider model, Google Tink primitive/keyset philosophy (highest operation decoupling but compile-time providers), AWS KMS and HashiCorp Vault Transit key rotation (same-algorithm only).
- **Academic/industry:** Cho et al. "Software-Defined Cryptography" (arXiv 2404.01808, CCS SCORED 2024); ELCA (Sikeridis, Kampanakis, USENIX Security poster 2023); SecAlgo (PLAS 2019); EverCrypt (S&P 2020); eUCRITE (2020); CARAF (J. Cybersecurity 2021); the Crypto-Agility Maturity Model / CAMM (Hohm/Heinemann/Wiesmaier, FPS 2023, arXiv 2202.07645); Näther et al. systematic review (ACM Comput. - **Patents (correction of a common error):** US 12,524,283 "Cryptographic agility through link layer abstraction" is assigned to **VMware, Inc.** (priority Indian application filed 16 Aug 2022) — **NOT IBM**. A related VMware patent, US 12,537,802, covers attestation/enforcement of cryptographic requirements across multiple hops with an "abstracted crypto API," "agility shim," "crypto provider," "policy manager," and "library manager." IBM's own crypto-agility IP centers on discovery/CBOM tooling (e.g., US 12,153,686 and US 12,229,279, CBOM generation from binaries) and Quantum Safe Explorer/Advisor products, not on a link-layer abstraction patent.

### G. Real-world figures for a research publication
- **Federal PQC migration cost:** OMB's July 2024 report to Congress (prepared with ONCD, CISA, and NIST under the Quantum Computing Cybersecurity Preparedness Act) states the "preliminary government-wide cost estimate for this migration, covering the period from 2025 to 2035, is approximately **$7.1 billion** (in 2024 dollars)" — a "rough order of magnitude" figure that excludes national-security systems, DoD, and the Intelligence Community (~$21 per person for ~335M population).
- **Enterprise migration cost/time:** private-sector internal migrations commonly cited at 2–4 years and **$8–25 million** depending on cryptographic footprint (with cryptographic-engineer median salary ~$285K); mid-market straightforward environments $500K–$8M. An MDPI expert-synthesis study projects **5–7 years (small), 8–12 years (medium), 12–15+ years (large)** enterprises.
- **Discovery phase:** for large enterprises the cryptographic-discovery phase alone runs 12–24 months; discovery budget ~$2–5M (large), $500K–$1.5M (mid). Testing can consume 25–40% of application-migration cost (one program hit 40% vs a 15% estimate).
- **HSM scaling:** PQC keys consume HSM capacity ~50× faster; enterprises may need 5–10× more HSM units; FIPS 140-3 module validation historically 12–24 months. Thales Luna Network HSM 7 ~$40K–60K/unit list; AWS CloudHSM ~$1.45/hr (~$12.7K/yr).
- **Crypto call-site scale:** the Applied Quantum PQC Migration Framework estimates 320+ cryptographic function calls in a single mobile-banking application; enterprise estates run to "hundreds of thousands" of cryptographic function calls / assets, most undocumented.
- **Historical precedents:** SHA-1→SHA-256 took ~10 years; per Microsoft's own bulletin, "beginning in August 2019, devices without SHA-2 support have not received Windows updates," and SHA-1-signed Windows content was retired from the Download Center on 3 August 2020 — over two years after the February 2017 Google/CWI SHAttered collision; SHA-1 collision cost was estimated at ~$75K–120K of cloud GPU rental by autumn 2015. SHA-1 has been disallowed for federal digital-signature generation since 2014; public CA/browser deprecation ran ~2013–2017.
- **API-misuse baseline:** Lazar et al. — 83% of cryptographic vulnerabilities across 269 CVEs were API-misuse (only 17% were primitive/algorithm-implementation flaws).
- **Regulatory/compliance forcing functions:** PCI DSS (strong-cryptography requirements), FIPS 140-3 module validation, CNSA 2.0 gates (2027/2030/2033), NIST IR 8547 (2030 deprecate / 2035 disallow), EU NIS2, EO 14144 TLS-1.3-by-2030.

## Recommendations
**Stage 1 — Position the contribution as the missing bridge and the missing rigor.** Frame the new work explicitly as connecting IBM's provider-API layer (bottom) to a governed control-plane/orchestration layer (top) — the exact seam both leave open — and/or as adding the empirical/formal rigor CCP lacks. Cite IBM 2606.13425/2606.13445 as the API-layer prior art and CCP as the enterprise-architecture prior art, and state plainly that they are independent and uncited-to-each-other. *Threshold to change plan:* if a v2 of either IBM paper or a CCP v1.0 appears that already specifies the orchestration/automation loop (E1.4/E2.3), pivot to the formal-verification or empirical-study angle instead.

**Stage 2 — Pick an original before/after domain that avoids both anchors.** CCP's example is **RSA/AES-256 policy migration** (architectural boxes, no code); IBM's is **RSA-PSS audit-log signing in Go** and an **ECDSA→ML-DSA audit-log** scenario. Deliberately avoid both signing-audit-logs and RSA-PSS-in-Go. Strong, differentiated candidates:
- **Database field-level encryption** (e.g., Java/JDBC `Cipher.getInstance("AES/GCM/NoPadding")` "before" → intent `scope=AEAD_WITH_AAD, purpose="encrypt PII column"` "after") — showcases C2.2 + re-encryption at scale.
- **mTLS between microservices** (hardcoded cipher suite / X.509 ECDSA "before" → policy-selected hybrid KEM "after") — bridges to the protocol-layer gap.
- **JWT/token signing in an identity provider** (`RS256` hardcoded in the JWK "before" → intent-based signing key with TransformKey to ML-DSA "after") — high call-site density, clear PQC stake.
- **Firmware image signing in an IoT fleet** (LMS/XMSS per CNSA 2.0) — ties directly to the 2030 firmware-signing deadline and constrained-device size pressures.
- **Payment message MAC generation** and **backup-archive encryption** — good for the FS-ISAC/PCI regulatory framing and streaming re-encryption.
Recommended primary example: **JWT signing in an IdP** or **DB field-level encryption**, because both maximize call-site count, map cleanly onto C2.2/E1.3, and are visually distinct from audit-log signing.

**Stage 3 — Ground every quantitative claim in the Section G figures** (the OMB $7.1B federal estimate; 5–15+ yr enterprise timelines; hundreds of thousands of call sites; SHA-1's ~10-yr, Microsoft-to-2019 precedent; 83% API-misuse; NIST 2030/2035 and CNSA 2027/2030/2033 gates) and correct the common VMware-vs-IBM patent error. *Threshold:* if pursuing a formal/empirical angle, add a measured artifact (a developer study, a latency benchmark across deployment modes, or a machine-checked substitutability proof) since that is precisely what neither prior work provides.

**Stage 4 — Differentiate visually.** CCP owns a distinctive dark-mode, lime-accent, serif+mono, clean-CSS-box look. If the new work is web-published, avoid that palette/aesthetic; the user's question of whether CCP is "hand-drawn/whiteboard" is answered — it is **not** — so a genuinely hand-sketched or light-mode editorial style would read as clearly independent.

## Caveats
- **arXiv IDs are unusual:** 2606.xxxxx implies a June 2026 submission; treat all "2606" references as mid-2026 preprints (v1, 11 Jun 2026). Both are workshop/preprint papers (MAgiCS @ Eurocrypt 2026), not yet archival journal versions; scores and the "6×" figure are the authors' own and not independently replicated.
