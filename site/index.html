A Common Crypto API

Ask for the outcome. Keep the crypto decision accountable.

The Crypto Agility Algorithm Protocol (CAAP) separates application intent from policy decisions, provider execution, key custody, and evidence—without pretending every algorithm or backend is interchangeable.

01 / Problem

Applications own cryptographic decisions that should change independently.

A call site often fixes the algorithm, parameters, provider API, key location, and encoding alongside the business operation. Policy changes then become application migrations, while backend differences leak into every consumer.

The bounded questionCan a caller express one precise cryptographic operation without receiving permission to select a weaker algorithm or bypass a custody requirement?
OperationAlgorithmParametersProviderKey locationEncoding

The goal is not “swap any algorithm anywhere.” The goal is to move eligible decisions behind a stable contract and reject every incompatible substitution explicitly.

02 / Precedent

CAAP composes established boundaries; it does not replace them.

NIST treats crypto agility as the ability to replace and adapt algorithms, protocols, standards, and implementations while preserving operations. Existing standards already define important provider and object boundaries. CAAP proposes the missing decision-and-evidence layer above them.

Operational guidance

NIST CSWP 39upd1

Frames crypto agility as a system capability involving inventory, policy, transition planning, testing, and operational tradeoffs.

Read NIST guidance

Provider boundary

PKCS#11

Defines a cryptographic token interface. A CAAP adapter may use it while preserving token mechanisms, sessions, object properties, and failures.

Read the OASIS specification

Managed-key boundary

KMIP

Defines managed cryptographic objects and operations. CAAP does not erase KMIP identifiers, states, usage masks, or result reasons.

03 / Definition

One specification. Two contracts. Five trust planes.

Research specification

Crypto Agility Algorithm Protocol

CAAP defines request semantics, policy resolution, enforcement invariants, provider dispatch, explicit failures, and evidence.

Consumer contract

Common Crypto API

Applications send a typed operation, intent, input, constraints, and context without naming a provider location or silently selecting a fallback.

Provider contract

Resolved execution

Adapters receive the exact approved primitive, parameters, opaque key reference, and evidence context after policy and capability checks.

Capability says what can execute now. Policy says what is permitted. Caller authorization remains a separate decision.

05 / How it works

Policy decides. The broker enforces. Ambiguity stops the request.

  1. Authenticate and authorizeEstablish tenant and workload context before capability disclosure.
  2. Validate the envelopeCheck version, freshness, request identifier, typed input, and unknown fields.
  3. Pin one policyResolve one active profile and reject absence, ambiguity, expiry, or downgrade.
  4. Resolve the keyValidate tenant, version, state, purpose, and opaque reference.
  5. Match capabilityRequire the exact operation, algorithm profile, provider class, and protection level.
  6. Dispatch onceExecute only the resolved operation; never silently substitute.
  7. Return typed outputPreserve operation-specific encoding and portable error categories.
  8. Emit evidenceCorrelate policy and execution without exposing keys or unintended payload data.
06 / Pillars

The contract is useful only if these properties survive every binding.

Typed operations

Message, digest, ciphertext, key material, and structured objects are never inferred from unlabelled bytes.

Pinned policy

Every accepted operation identifies one active profile and version used for the decision.

Opaque keys

Private material stays with its provider by default; references are scoped and tenant-bound.

Fail closed

Ambiguity, expiry, downgrade, capability mismatch, and invalid key state produce explicit failures.

Scoped discovery

Capabilities are freshness-bounded execution facts, not caller authorization or a policy bypass.

Portable evidence

Results name decision and execution context without logging secrets, raw keys, or unnecessary payloads.

08 / Why now

Cryptographic change is arriving faster than application change.

Algorithm transition

Post-quantum migration and ordinary deprecation both require controlled coexistence, evidence, and rollback decisions.

Provider diversity

Software, HSM, managed KMS, platform key stores, and remote services expose different capability and custody semantics.

Policy accountability

Organizations need to explain which rule authorized an operation and what actually executed.

CAAP treats agility as an operational property of the system—not an algorithm selector added to every application call.

09 / Limits

The abstraction must expose mismatches, not conceal them.

Does not replace

Protocols and providers

CAAP does not replace PKCS#11, KMIP, cloud KMS APIs, cryptographic libraries, certificate authorities, or application protocols.

Does not prove

Custody from opacity

An opaque reference alone does not prove hardware protection, non-exportability, attestation, or portability.

Requires definition

Combined cryptography

A reviewed construction must fix algorithms, parameters, combiner, byte encoding, validation, partial failure, and assumptions.

Creates successors

Migration

Cross-algorithm evolution normally creates new key material and a new version; it is not mathematical conversion of an existing key.

10 / Implementation

A narrow reference service makes the contract testable.

The Python service demonstrates one artifact-signing profile with a software provider. It is intentionally small enough to inspect and strict enough to expose unresolved contract questions.

HTTP / JSON
GET /v1/capabilities
POST /v1/policies:resolve
POST /v1/keys
GET /v1/keys/{keyRef}
POST /v1/sign
POST /v1/verify
  • Algorithm: Ed25519
  • Provider: in-memory Python software adapter
  • Keys: opaque, tenant-bound references; public material only in responses
  • Policy: exact profile and version pinned into each decision
  • Tests: positive and negative broker/contract coverage
  • Authentication: optional development bearer token, disabled by default
